# Feature Specification: 통합 보드 (Unified Board)

**Feature Branch**: `feat/unified-board`
**Created**: 2026-10-15
**Status**: Draft
**Input**: User description: "등록된 모든 프로젝트의 칸반과 에이전트 상태를 한 화면에서 보고 조작한다. 프로젝트마다 포트/프로세스를 띄우지 않고 하나의 프로세스·포트로 운영해 자원을 아낀다. ~/Documents/_shin 아래 새 저장소는 자동 등록. 기본 에이전트는 Claude Code."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 모든 프로젝트를 한 화면에서 본다 (Priority: P1)

프론트엔드 개발자인 사용자가 브라우저 주소 하나를 열면 등록된 모든 프로젝트의 티켓이 하나의 칸반(같은 상태 칸: Todo / In Progress / Verify / Document / Human Review / Done …)에 섞여 보인다. 각 카드에는 어느 프로젝트 소속인지와 에이전트 실행 여부(턴 수, 마지막 이벤트)가 표시된다. 프로젝트 사이를 오가지 않아도 "지금 어디서 무엇이 돌고, 무엇이 내 확인을 기다리는지"를 한눈에 안다.

**Why this priority**: 사용자의 핵심 불만("그때그때 가서 보면 지금과 다른 게 뭐냐")을 직접 해결한다. 이것만 있어도 가치가 있다.

**Independent Test**: 티켓이 있는 프로젝트 2개 이상을 등록하고 통합 화면을 열어, 두 프로젝트의 카드가 한 보드에 프로젝트 표시와 함께 보이는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 프로젝트 A(티켓 2개)와 B(티켓 3개)가 등록됨, **When** 통합 화면을 연다, **Then** 5개 카드가 상태 칸별로 보이고 각 카드에 프로젝트 이름이 표시된다.
2. **Given** 프로젝트 B의 티켓 하나를 에이전트가 실행 중, **When** 통합 화면을 보고 있다, **Then** 새로고침 없이 그 카드에 실행 중 표시와 턴 수가 갱신된다.
3. **Given** 통합 화면, **When** 프로젝트 필터에서 A만 고른다, **Then** A의 카드만 보인다.
4. **Given** 에이전트가 사용자에게 질문해 티켓이 Human Review로 이동, **When** 통합 화면을 보고 있다, **Then** 해당 카드가 Human Review 칸에 눈에 띄게 표시된다.

### User Story 2 - 하나의 프로세스로 모든 프로젝트를 돌린다 (Priority: P1)

사용자가 명령 하나(또는 로그인 시 자동 실행)로 서버 하나를 켜면, 모든 등록 프로젝트의 오케스트레이션이 그 한 프로세스·한 포트 안에서 돌아간다. 프로젝트별 포트(10000, 10001…)와 프로세스가 더 이상 필요 없다.

**Why this priority**: 현재 프로젝트마다 약 57MB 프로세스가 따로 뜬다. 프로젝트가 늘수록 자원이 선형으로 늘어나는 문제를 없앤다. US1의 통합 화면도 한 프로세스가 모든 상태를 쥐고 있어야 자연스럽다.

**Independent Test**: 프로젝트 7개 등록 상태에서 통합 서버를 켜고, 실행 중인 Symphony 관련 프로세스가 1개, 열린 포트가 1개인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 등록 프로젝트 7개, **When** 통합 서버를 시작한다, **Then** Symphony 프로세스는 1개, 리슨 포트는 1개다.
2. **Given** 통합 서버 실행 중, **When** 한 프로젝트의 티켓 실행이 실패한다, **Then** 다른 프로젝트의 오케스트레이션은 영향받지 않는다.
3. **Given** 통합 서버 실행 중, **When** 사용자가 통합 화면에서 프로젝트 하나를 일시정지한다, **Then** 그 프로젝트는 새 티켓을 가져가지 않고 나머지는 계속 돈다.
4. **Given** 아무 에이전트도 돌지 않는 유휴 상태, **When** 메모리를 측정한다, **Then** 프로젝트 수와 거의 무관하게 단일 프로세스 수준에 머문다.

### User Story 3 - 새 프로젝트를 자동으로 등록한다 (Priority: P2)

사용자가 `~/Documents/_shin` 아래에 새 git 저장소를 만들거나 클론하면, 별도 조작 없이 몇 분 안에 통합 보드에 그 프로젝트가 나타난다(기본 에이전트 Claude Code).

**Why this priority**: 편의 기능이다. 수동 등록 명령으로도 대체 가능하다.

**Independent Test**: 통합 서버 실행 중 감시 폴더에 빈 git 저장소를 만들고, 일정 시간 안에 통합 화면 프로젝트 목록에 나타나는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 통합 서버 실행 중, **When** 감시 폴더에 새 git 저장소를 만든다, **Then** 5분 이내에 프로젝트로 등록되어 통합 화면에 보인다.
2. **Given** 감시 폴더에 git이 아닌 폴더·워크트리·제외 목록 폴더가 생긴다, **When** 감지 주기가 돈다, **Then** 등록하지 않는다.
3. **Given** 등록 시도가 실패한 폴더(예: `Docs/` 대소문자 충돌), **When** 다음 주기가 돈다, **Then** 같은 폴더를 반복 시도해 저장소를 건드리지 않는다(실패 기록 후 건너뜀).

---

### Edge Cases

- 등록 프로젝트의 폴더가 삭제·이동된 경우: 통합 화면에서 "찾을 수 없음"으로 표시하고 다른 프로젝트 동작은 유지한다.
- 두 프로젝트에 같은 티켓 ID(예: TASK-1)가 있는 경우: 카드와 조작이 프로젝트로 구분되어 섞이지 않는다.
- 기존 개별 서비스(포트 10000번대)가 이미 떠 있는 상태에서 통합 서버를 켜는 경우: 같은 프로젝트를 두 오케스트레이터가 동시에 돌리지 않도록 막고 사용자에게 알린다.
- 프로젝트 수가 많아(20개 이상) 카드가 많은 경우: 필터·접기로 화면이 쓸 만해야 한다.
- 통합 서버를 재시작한 경우: 진행 중이던 티켓은 기존 재시작 안전 동작(크래시 이어하기)을 그대로 따른다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 등록된 모든 프로젝트의 티켓을 하나의 칸반 화면에 상태별로 모아 보여주어야 한다.
- **FR-002**: 각 카드는 소속 프로젝트, 티켓 ID·제목, 실행 상태(실행 중/재시도 대기/완료), 턴 수, 마지막 이벤트를 표시해야 한다.
- **FR-003**: 통합 화면은 새로고침 없이 실행 상태 변화를 수 초 이내에 반영해야 한다.
- **FR-004**: 사용자는 통합 화면에서 프로젝트별로 필터링하고, 프로젝트별 오케스트레이션을 일시정지/재개할 수 있어야 한다.
- **FR-005**: 사용자는 통합 화면에서 프로젝트를 지정해 새 티켓을 만들 수 있어야 한다.
- **FR-006**: 사용자는 카드를 열어 해당 티켓의 상세(본문, 실행 기록)를 볼 수 있어야 한다. 기존 프로젝트별 상세 기능(Git 리뷰, 미리보기, 채팅 등)은 프로젝트 상세 화면으로 이동해 쓸 수 있으면 충분하다.
- **FR-007**: 시스템은 모든 등록 프로젝트의 오케스트레이션을 하나의 프로세스와 하나의 포트에서 수행해야 한다.
- **FR-008**: 한 프로젝트의 오류·실패가 다른 프로젝트의 오케스트레이션을 멈추게 해서는 안 된다.
- **FR-009**: 동일 프로젝트를 둘 이상의 오케스트레이터가 동시에 실행하지 못하게 막아야 한다.
- **FR-010**: 시스템은 감시 폴더(기본 `~/Documents/_shin`) 아래 새 git 저장소를 주기적으로(최대 5분 간격) 감지해 자동 등록해야 한다. 워크트리·비-git 폴더·제외 목록은 건너뛴다.
- **FR-011**: 자동 등록에 실패한 폴더는 기록하고 이후 주기에서 다시 시도하지 않아야 한다(사용자가 수동으로 재시도 가능).
- **FR-012**: 새로 등록되는 프로젝트의 기본 에이전트는 Claude Code여야 한다.
- **FR-013**: 기존 프로젝트별 실행 방식(`symphony service start`, 프로젝트별 포트)은 계속 동작해야 한다(통합 모드는 추가 기능).

### Key Entities

- **프로젝트(Project)**: 등록된 저장소 하나. 이름, 경로, 워크플로 파일, 일시정지 여부, 상태(정상/찾을 수 없음/오류).
- **티켓(Ticket)**: 프로젝트의 칸반 항목. 프로젝트 + 티켓 ID로 유일하게 식별. 상태 칸, 제목, 우선순위.
- **실행(Run)**: 티켓에 대한 에이전트 실행. 상태, 턴 수, 토큰, 마지막 이벤트.
- **감시 폴더(Watch Root)**: 자동 등록 대상 상위 폴더와 제외 목록, 실패 기록.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자는 주소 하나만 열어 모든 프로젝트의 진행 상황을 확인할 수 있다(프로젝트 화면 이동 0회).
- **SC-002**: 프로젝트 7개 등록 시 Symphony 관련 프로세스 1개, 리슨 포트 1개로 동작한다(현재: 프로젝트당 1개씩).
- **SC-003**: 프로젝트 7개를 모두 활성화한 유휴 상태에서 총 메모리가 현재 방식으로 프로젝트 3개를 켰을 때(약 170MB)보다 작다.
- **SC-004**: 에이전트 실행 상태 변화가 통합 화면에 5초 이내 반영된다.
- **SC-005**: 감시 폴더에 새 git 저장소를 만들면 5분 이내에 통합 화면에 나타난다.

## Assumptions

- 단일 사용자, 로컬 전용(127.0.0.1) 사용이다. 인증은 기존 로컬 보호(루프백 바인딩, 호스트 검사) 수준을 그대로 따른다.
- 트래커는 파일 기반 칸반(`kind: file`)만 통합 대상이다. Linear/Jira 프로젝트는 이번 범위에서 제외한다.
- 에이전트 동시 실행 수 제한은 프로젝트별 기존 설정을 그대로 쓴다. 전역 동시 실행 상한은 이번 범위에서 다루지 않는다.
- 통합 서버를 로그인 시 자동 실행하는 방법은 macOS 문서 폴더 접근 권한을 가진 방식이어야 한다. launchd + zsh는 TCC에 막힌 것이 확인됐다.
- UI는 기존 웹 관리 화면(바닐라 JS)의 스타일·구조를 재사용해 확장한다. 별도 프론트엔드 프레임워크 도입은 계획 단계에서 판단한다.
- `oh-my-symphony`는 개인 포크(yeo11200)로 운영하며 업스트림 동기화는 이번 범위가 아니다.
